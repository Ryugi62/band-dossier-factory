| D1 | Which providers does stage 1 call? | "Nimble is the default provider: every service must be able to research companies using Nimble alone. | D2 | Is a Nimble research run part of every build? | "The **evidence** for a company is every page that some search ... returns, with its full text, and every claim that a `nimble` research run for the company asking for all six fields answers with." and "each field is `known` exactly when the evidence (§4) supports a value for it" | Every build starts one Nimble research run asking for all six fields (25 units) unless the 80-unit cap forbids it; its claims are asserted only when the claim's own citation passes the Appendix A support rule, checked locally by the service. | builder, verifier, cost-auditor |
| D3 | When several values are supported for a field, which one is held? | "When the evidence supports more than one value for a field, the field holds one of them and cites only excerpts that support that value." | Any one is allowed; the service picks deterministically: the value supported by the most distinct pages, ties broken by the value gathered first. Citations are only excerpts supporting that value. Verifier probes must accept any supported value. | builder, verifier |
| D4 | Does `spent_units` count calls of a running build? | "`spent_units` is the total cost (§9) of every provider call made for this dossier, by every build, since it was created." | Each call's cost is added to `spent_units` when the call is made (or fails by timeout/connection, which costs its units); calls refused with an error status add 0. A read during a build shows the spending so far. | builder, verifier, cost-auditor |
| D5 | Is the 80-unit cap per dossier or per build? | "No build of a dossier spends more than 80 units (§9)." | Per build; `spent_units` is cumulative across builds. The service reserves worst-case cost before each call and stops when the next call would exceed 80. | builder, cost-auditor |
| D6 | Replay of `POST /dossiers` that originally returned 200 (dossier existed)? | "Replay: same key, same body → **200**, body identical to the original response as a JSON value" | Stored response (status and body) is returned with status 200 on replay, even if the first answer was 202 or 200. | builder, verifier |
| D7 | Implementation language? | "Python is not required in the implementation. TypeScript/JavaScript, Go, Rust, Java, Python and any other language are equally valid." | Builder's choice. Planner's recommendation: Python (calls `web_router` in-process; no helper process). | builder |
| D8 | Where do citations of a research claim come from, and are research excerpts kept? | "The claim is asserted only when its citation supports it." | A research claim becomes a citation (`provider: nimble`, `url`, `excerpt`) only if the excerpt is copied from text the service holds for that url (served by a provider to this service, prose not header; the service may fetch the page with a 1-unit Nimble extract to hold it) and passes Appendix A for the claimed value; otherwise the claim is dropped. | builder, verifier |

| D25 | What does a stage-2 export hold, and what follows for the build log? | "State imported from a stage-2 export keeps the builds that the stage-2 service made, each with its time, its outcome and its spending." | The closed stage-2 export (frozen at 3e32ac8) holds per dossier only the last settled state (fields with candidates incl. kind, published_at, retrieved_at, provider; researched_at; spent_units) and no earlier builds, no `Effective` lines. So the only build it can keep is the one the spec gives for state a stage-2 service itself imported: one build that completed `ready` at `researched_at` (its spending = the exported `spent_units`), its candidates are the exported ones with `learned_at` = their `retrieved_at`, and one page version per candidate URL whose `true_from` is the UTC date part of the candidate's `published_at`, null when that is null. A stage-1 export is handled as D16 plus the spec text (candidates have null published_at, so `true_from` null). A dossier with null `researched_at` has no build. | builder, verifier |
| D26 | What is a stage-3 export? | "the history and feed of a stage-3 export survive a stage-3 import unchanged. So do its builds" | `format_version` stays 1, `track` "dossier"; the state holds users, tokens, dossiers (settled state), every build (time, outcome, spending, candidates, page versions), history, feed entries with their `seq` and the next `seq`, first-seen map for `learned_at`, idempotency records. Import accepts the three shapes (stage-1, stage-2 and stage-3 state, told apart by their content). `executives` is `unknown` in imported state from stage-1/2 exports, in every build kept from them, with no history entry. | builder, verifier |
| D27 | How is durable state done and what happens to a build interrupted by an abrupt stop? | "The container may be stopped abruptly at any time, with no warning ... When no build is running at the stop, the service answers after the restart exactly as it did before the stop" | State lives in a durable store on the container's own filesystem (not a declared volume), every write committed (flushed to disk) before its HTTP response; start-up reads it (health within 60 s). The clock's set time (from reset or `/_test/clock`) is persisted and read back as the same instant (frozen); a clock never set keeps following system time. A build found running after restart is closed as abandoned: the dossier returns to its last completed state (or `failed` with all fields `unknown` when none), the spending recorded before the stop stays in `spent_units`, and it adds no history, no feed entry and no build log entry. Reset replaces the stored state; `docker rm` loses it. | builder, verifier |
| D28 | Feed numbering and reset | "`seq` is a positive integer, unique across the feed, and larger for every later entry." | `seq` starts at 1 after reset and after an import of a stage-1/2 export (empty feed); a stage-3 import restores the feed and continues from its next `seq`. Seq never repeats within the life of the current state. | builder, verifier |
| D29 | Order of validation and lookup | "A required field or query parameter is missing, or a stated rule is violated with no more specific code" (§5) and the 404 rows of `as_of`, `values` | Auth (401) first; then parameter validation (422) before existence (404): a bad `as_of`/`true_at`/`since`/`limit` for an unknown domain is 422. `as_of` and `true_at` comparisons use instants (offsets normalised) and calendar dates; `true_at` must be a real calendar date. | builder, verifier |
| D30 | Executives in the UI and `/contested` | "`executives` takes none of them, and a screen that shows it does so with other markup. On `/contested`, 'no field is contested' means none of those six fields is." | The dossier and evidence screens keep exactly the six `field-*`/`evidence-*` testids of stage 2 and additionally show `executives` (members, status, citations, candidates) in separate markup with new, non-conflicting testids (e.g. `executives-panel`). `/contested` considers the six fields only. | builder, verifier |
| D31 | Evidence for executives and the cap | "A research run (§4) still asks for the six fields of §4 only." | Executives candidates come only from rendered page text (D13) via Appendix A with the title phrases; research claims are never executives candidates. The 80-unit cap per build is unchanged, so which extra pages are searched and rendered is the builder's economy decision; the cost auditor compares units per correct item with the stage-2 figure (8.935) and accepts increases only where the new requirement forces them. | builder, cost-auditor |
| D32 | `learned_at` of a selected value that stays selected | "For a selected value, it is the time of the build that made it the selected value." | When a build keeps the same selected value as the build before, `learned_at` stays the time of the build that first made it selected in the current run of that value; if the value was selected, replaced and selected again, it is the time of the build that made it selected again. History entries are added only on a differing selected value (spec: "adds nothing for it, even when its candidates, citations or `true_from` differ"). | builder, verifier |
| D33 | Does a page version with null `true_from` hold on every date or on no date? (verifier question T5-05) | "A version whose `true_from` is null holds from no date, and a later version with a null `true_from` replaces every earlier version of its URL." | It holds on no date: its candidates are never among the candidates at any `true_at`. It still takes part in replacement and ending of other versions as the sentences state (a later version with null `true_from` replaces every earlier version of its URL; a gathered version without candidates still replaces or ends earlier versions). A version with a null `true_from` is not an "earlier version that it does not replace" whose end date can be computed, so it never stops another version. | verifier, builder |
