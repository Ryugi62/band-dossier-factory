| id | question | quoted sentence | decision | sent to |
|---|---|---|---|---|
| D1 | Which providers does stage 1 call? | "Nimble is the default provider: every service must be able to research companies using Nimble alone. Tavily is optional" | Stage 1 calls Nimble only; Tavily is never called (its searches cost 8-16 units, extracts 2). `TAVILY_*` variables are accepted and ignored. | builder, verifier, cost-auditor |
| D2 | Is a Nimble research run part of every build? | "The **evidence** for a company is every page that some search ... returns, with its full text, and every claim that a `nimble` research run for the company asking for all six fields answers with." and "each field is `known` exactly when the evidence (§4) supports a value for it" | Every build starts one Nimble research run asking for all six fields (25 units) unless the 80-unit cap forbids it; its claims are asserted only when the claim's own citation passes the Appendix A support rule, checked locally by the service. | builder, verifier, cost-auditor |
| D3 | When several values are supported for a field, which one is held? | "When the evidence supports more than one value for a field, the field holds one of them and cites only excerpts that support that value." | Any one is allowed; the service picks deterministically: the value supported by the most distinct pages, ties broken by the value gathered first. Citations are only excerpts supporting that value. Verifier probes must accept any supported value. | builder, verifier |
| D4 | Does `spent_units` count calls of a running build? | "`spent_units` is the total cost (§9) of every provider call made for this dossier, by every build, since it was created." | Each call's cost is added to `spent_units` when the call is made (or fails by timeout/connection, which costs its units); calls refused with an error status add 0. A read during a build shows the spending so far. | builder, verifier, cost-auditor |
| D5 | Is the 80-unit cap per dossier or per build? | "No build of a dossier spends more than 80 units (§9)." | Per build; `spent_units` is cumulative across builds. The service reserves worst-case cost before each call and stops when the next call would exceed 80. | builder, cost-auditor |
| D6 | Replay of `POST /dossiers` that originally returned 200 (dossier existed)? | "Replay: same key, same body → **200**, body identical to the original response as a JSON value" | Stored response (status and body) is returned with status 200 on replay, even if the first answer was 202 or 200. | builder, verifier |
| D7 | Implementation language? | "Python is not required in the implementation. TypeScript/JavaScript, Go, Rust, Java, Python and any other language are equally valid." | Builder's choice. Planner's recommendation: Python (calls `web_router` in-process; no helper process). | builder |
| D8 | Where do citations of a research claim come from, and are research excerpts kept? | "The claim is asserted only when its citation supports it." | A research claim becomes a citation (`provider: nimble`, `url`, `excerpt`) only if the excerpt is copied from text the service holds for that url (served by a provider to this service, prose not header; the service may fetch the page with a 1-unit Nimble extract to hold it) and passes Appendix A for the claimed value; otherwise the claim is dropped. | builder, verifier |
| D9 | `USD12m` (no space): an amount? (verifier note 3, round 1) | "`$`, `US$` or `USD`, an optional space, a number" versus "Digits directly next to a letter, or joined to other digits by `,` or `.` in any other way, are not a number." | Waived as spec-ambiguous and rare: the service keeps the literal reading (digits directly after a letter are not a number, so no amount). Verifier oracle and probes must not rely on `USD<digits>` without a space. | verifier, builder |
| D10 | Round 1 notes 1, 2, 4 owners | review r1 notes | Note 1 (live path untested offline) and note 4 (10 s bound under refusals) go to builder as non-blocking work with the F1 fix; note 2 (evidence beyond the domain search) is waived: the service already runs extra searches when the domain search returns 10 results or fails, and the spec defines "gathers" as what a build obtains. | builder |
| D11 | Owners of the round 2 non-blocking notes | verifier r2 notes 1-2, cost-auditor advisory | Waived, with reasons. V-note 1 (`BUILD_HARD_LIMIT` backstop marks `failed` even if some calls succeeded): every call already ends by 290 s, so the 298 s backstop should never fire; changing it would need a new commit and a new review round for no observable effect. V-note 2 (no retry of refused calls after about 4.9 s off the live endpoint): harmless in stage 1 (probes and shipped checks pass); recorded as a carry-over for the builder in the next stage, not acted on now. Cost advisory (research run is 78% of units; live branch not measurable offline): mandated by D2 and bounded by the 80-unit reservation, no action. | builder (carry-over), waived otherwise |

| D12 | Which stage-1 decisions still apply? | "The stage-1 requirements continue to apply, with the additions below." | D1, D2, D4, D5, D6, D9, D10, D11 continue. D3 (pick any one value) is replaced by the spec's selection rule. | D13 | Where must citation excerpts come from? | "Evidence (§4) is read from page text so defined, and a citation's excerpt must appear in the page's text." and "provider_options={\"render\": True} on WebRouter's extract." | Every excerpt of every candidate must appear in the browser text of its page, obtained by a Nimble extract with `render: True` (3 units per URL). Search snippets and plain extracts may only be used to choose which URLs to render. Which URLs to render within the 80-unit cap is the builder's economy decision. | builder, verifier, cost-auditor |
| D14 | Kernel and Browserbase? | "neither browser vendor is required." | Not used. Tavily stays unused (D1). | builder |
| D15 | 429 handling | "The same call ... made again less than one second after a 429 ... is answered 429 again. No call is answered 429 more than three times in a row" and "Time a build spends waiting to make a call again after a 429 does not count toward the 10 seconds". | A call answered 429 is repeated after waiting at least 1.1 s, up to 4 attempts in all (three refusals then an answer); the stage-1 rule that stops retrying about 5 s into a build (verifier note, D11) is removed; refusals cost 0 and are not duplicates. Unit price of a repeated call counts only for the attempt that is answered. A build whose calls answer within one second ends within 10 s plus its 429 waiting time, and still within 300 s on the live endpoint. | builder, verifier, cost-auditor |
| D16 | What can an imported stage-1 dossier's candidates be built from? | "Each imported field gains one candidate for every value that text the providers served to the dossier's last stage-1 build that completed `ready` supports for that field ... its `kind` and `published_at` are as the exported state records them or else null, and its `retrieved_at` is the dossier's `researched_at`." | The stage-1 export (frozen at 9166a28, stage-1/ is never changed) records per field only the value and its citations (url, excerpt, provider). Those excerpts are the only served text it holds. So: one candidate per exported citation whose excerpt supports the field's value under Appendix A (checked at import); `provider` as exported; `kind` null (authority of aggregator) and `published_at` null; `retrieved_at` = `researched_at`; a field with value null has no candidates. Value, status, citations then follow from the selection rule. | builder, verifier |
| D17 | Export format of stage 2 | "A stage-2 service must accept an export produced by the same team's stage-1 service." and stage-1 §10 | `format_version` stays 1, `track` "dossier". The stage-2 state stores candidates; import accepts both shapes (fields without `candidates` = stage-1 export, rebuilt as D16; fields with `candidates` = stage-2 export, restored as exported). Tokens, users, idempotent records are retained as in stage 1. | builder, verifier |
| D18 | Auth and HTML negotiation | "Return the UI for `Accept: text/html`; API requests without that header receive JSON." | A request whose `Accept` header lists `text/html` for `/`, `/signup`, `/login`, `/dossiers/{domain}`, `/dossiers/{domain}/evidence`, `/contested` receives the UI document with status 200 and no bearer check (a browser navigation cannot send one); the UI reads data with `fetch` using the bearer token kept in browser storage, and sends a signed-out visitor to `/login`. API requests stay authenticated (401 as in stage 1). A domain that is invalid or has no dossier shows `dossier-not-found`. | builder, verifier |
| D19 | How many candidates per page? | "Every value that a page of the evidence (§4) supports for a field is a candidate of that field, once for each such page." | One candidate per (url, provider, value) of a field: the first supporting sentence of the page's browser text, in text order, is its excerpt. | builder, verifier |
| D20 | What is an "unknown outcome" in the UI? | "If a research or refresh response is lost, including after the request commits, show `research-uncertain` or `refresh-uncertain`" | A request that produced no HTTP response (network error, abort, timeout) or a 5xx is uncertain; any HTTP 4xx is a refusal (`research-error` / `refresh-error`). The UI keeps the key and body of the pending request and retries with the same ones. | builder, verifier |
| D21 | UI assets | "external services other than the provider endpoints this specification lists are unavailable at runtime." | All UI code, styles and fonts are inside the image; no CDN, no web fonts from the network; system font stack. | builder |
